# ADR 0051: mods, Julia packages that react to events and draw where Ship of Tools draws

**Status:** current — Accepted 2026-10-26 (proposed 2026-10-18, revised 2026-10-19 and 2026-10-26), built in a 0.7.Z
after the 0.7.0 tag; nothing below is built. It supersedes ADR 0006 and ADR 0007, and the build commit marks them so.

**Date:** 2026-10-18

## Context

The maintainer, 2026-10-17: "should we do our own mod system that takes advantage of sot and forget about desktop
compat? I like killer apps that we can do that desktop or cli can't. … mod is just something that runs hook after any
event and updates. We could compose just about anything with that concept in SoT and potentially add more sot features
to do it with more ease and/or capabilities."

- A Claude Code mod is middleware around one session's events (before, block, rewrite, after), plus an engine handle
  (state, store, timers, files, processes, model calls, subagents, commands, tools), plus drawing on that session's own
  surfaces. An earlier study, kept outside the repository, designed one TypeScript mod that would draw in Claude Code
  Desktop and hand the same SVG to the window as a file. The maintainer dropped desktop compatibility, so that route is
  not built.
- Ship of Tools sees what no single session can: every row on every computer and the agent in it, REPL runs and their
  figures, file changes, mail and work-state, the host monitor. It draws where no session can: the navigation trees and
  the preview pane, with CairoMakie figures among what it draws.
- The extension model is multiple dispatch (`docs/src/extend/abi.md`): a package extends Ship of Tools by being
  `using`-ed, with no manifest and no registration. `FileType` is built. `Mode`, `ConceptEntity`, `AnnotationKind`,
  `Tool` and `Capture` are declared in `core/src/ConceptExplorerCore.jl`, and nothing implements them.
- The requirements ask that the user always see what each active agent is doing and what state it is in, and inspect
  its actions afterwards (`requirements.md:52-53`). The environment imposes no permission tiers, sandboxes or rule-based
  gating (`requirements.md:62`), and it must not assume a fixed tool surface (`requirements.md:92`).

## Decision

A mod is a Julia package that defines a subtype of `Mod` and methods on it. One Julia process per daemon, the mod host,
loads the shipped mods and the person's own mods environment, and nothing else. Events reach a mod as `Event{K}`
values, and a mod receives a kind only when it has a `react` method for it, so subscription is dispatch. Agents record
their own events: each Claude Code hook event starts a short `sotd agent-record` process that appends one line to its
row's agent record, a file the host reads as a queue, so the daemon carries no agent event and the record outlives
every process. A mod draws by answering `tree_children` and
`preview` for its own node ids; the window shows every mod in one generic Mods navigation mode with the tree and the
image, markdown and text renderers it already has, and learns no mod. Mods observe and never gate: there is no before,
block or rewrite.

## The mod

A sketch (the helpers it calls are the mod's own):

```julia
module AgentsView
using ConceptExplorerCore
import ConceptExplorerCore: react, tree_children, preview

mutable struct Agents <: Mod
    rows::Dict{String,RowState}
end
Agents() = Agents(Dict{String,RowState}())   # one instance, on the mod's own task; history arrives as events

react(m::Agents, e::Event{:rows}) = (sync_rows!(m, e.data); changed(m, ""))
react(m::Agents, e::Event{:agent}) = (record!(m, e); changed(m, e.row))

tree_children(m::Agents, id::AbstractString) = id == "" ? row_nodes(m) : subagent_nodes(m, id)
preview(m::Agents, id::AbstractString, params::AbstractDict) =
    PreviewPayload("image/png", timeline_png(m, id, params["fit_w"], params["fit_h"]), Dict{String,Any}())
end
```

Core gains, beside `FileType`, declarations only: they add no I/O to core and no wire op (core is in sidecars'
contract, `rust/backend/src/sidecars/CLAUDE.md`).

| Name | What it is |
|---|---|
| `Mod` | the abstract type a mod subtypes; the host makes one instance of each concrete subtype with `M()` |
| `Event{K}` | one event: `row` (a workspace id, or `nothing`), `t` (the source's own time), `data` (the source's JSON, as a `Dict`) and `dropped` (how many events of this mod's queue gave way since the last it received); `K` is the kind, a `Symbol` |
| `react(m, e)` | the hook; core defines no method, so a mod hears only the kinds it names. Not exported, so it never meets Makie's exported `on` |
| `tree_children(m, id)` | the mod's nodes under `id` (`""` is its root), as `TreeNode`s; default none |
| `preview(m, id, params)` | a `PreviewPayload` for one of its nodes: the 3-argument form a `FileType` answers, its params carrying the pane's `fit_w` and `fit_h` |
| `changed(m, ids...)` | tells every window showing those nodes to fetch them again; declared in core, its method is the host's |

Removing an exported name is an interface break. This record was accepted before the 0.7.0 tag, so `Mode`, `Tool` and
`Capture` are removed before that tag, riding the break 0.7.0 already makes. Should the removal miss the tag, they are
marked deprecated in their docstrings and in the manual in the 0.7.Z that builds mods, and removed in 0.8.0.

## Where mod code runs: the mod host

- One Julia child per daemon, `julia/mods/` (`ShipToolsMods`), owned by sidecars, with its supervisor in
  `rust/backend/src/sidecars/mods/`, a folder with its own page. It is a user-code child, so it gets what the REPL
  gets: `ChildTmp::for_user_code`, and on Linux a display of its own, whose end signals every process that holds it
  (sidecars guarantee 15, with the limits stated there). It is supervised by the sidecars contract's child rules, as
  the kernel is: started through `Signal::spawn` under the daemon's `Signal`, its lines read through `ChildLines`, its
  last stderr lines kept, and its restarts paced by platform's `Redial`, from 250 ms doubling to 30 s. Its start
  bound covers a cold precompile; julia comes from `julia::resolve_bin`, with `--startup-file=no`. It speaks NDJSON
  over its stdio with its own protocol version checked at hello. The daemon passes its answers on, and the window
  builds every `TreeNode` from their JSON, in Rust, as it builds the Modules tree from the kernel's
  (`rust/frontend/src/ui/nav/modules.rs`). It starts when the daemon serves, whatever lifecycle decides for the rows,
  and ends with the daemon.
- What it loads: exactly `JULIA_LOAD_PATH=<shipped project>:<mods environment>:@stdlib` (`;` on Windows), with
  `JULIA_PROJECT` removed and a working folder of its own, so the person's default environment, a `JULIA_PROJECT` and
  every project folder are off its path. The shipped project is prepared at install and update like the kernel's: an
  entry in the installer's list of environments (`ENVS`, `rust/backend/src/install/julia.rs`) and in the updater's
  instantiate and load-test lists (`rust/updater/src/prepare.rs`). It holds the host, core, the shipped mods as
  `[sources]` dependencies, and CairoMakie. The mods environment is
  `<config dir>/mods/` (`~/.config/sot/mods/`; on Windows `%LOCALAPPDATA%\sot\config\mods\`), made by the installer,
  which writes no entry in it but core's. The host `using`s each package in its `[deps]`. Core must resolve there on
  every computer that shares the home, after an install prefix moves too. A `Pkg.develop` path records one computer's
  prefix, the failure the kernel's own project records (`julia/kernel/Project.toml`). So item 1 settles how core is
  found, a `[sources]` entry the installer rewrites or core registered by name, against its done test.
- Julia takes a package from the first environment on that path whose manifest has it, so a person's mod that was
  resolved against another version of a package the shipped project also holds (CairoMakie, say) loads the shipped
  version. The host reads both manifests at start and names each such package on the mod's health line. It never runs
  Pkg: a package not installed on this computer is reported with the one command that installs it.
- Mods are the concrete direct subtypes of `Mod` after loading, one level, the rule `file_types()` already uses. An
  abstract subtype is named on its package's health line and not searched below.
- Not the kernel: it runs no user code and loads only the plugins its own project names (sidecars guarantees 2 and
  19), and mods leave that as it is. Not the REPL: it runs one eval at a time, shares `Main` with the person, and
  belongs to one row, so a mod that watches every row cannot live in one, and its handlers would wait behind the
  person's evals. Not the window:
  it is Rust, it closes while rows run on, and a computer's facts belong to its daemon.
- One instance, one task and one queue per mod; the constructor runs on that task too, so a slow or failing start
  delays or fails that mod alone. Its events and the window's requests for its nodes enter its queue in arrival order,
  so a mod's state needs no lock. Every handler, `tree_children` and `preview` is called through `Base.invokelatest`,
  so a method a mod adds after it loaded (an extension that loads with CairoMakie, an `@eval`) is reached.
- The wire: the REPL shim's guard (`point_stdout_away_from_wire!`, `julia/repl/src/frames.jl`) runs before any mod
  loads, so a mod's `println` or `display`, or a package that prints as it loads, goes to stderr; and one writer, the
  serve loop, writes every line, `changed` included, which the mods' tasks hand it over a channel.
- What a stalled mod costs, stated as Julia gives it: the serve loop runs on the interactive thread and the mods on a
  default pool of two threads (`--threads=2,1`). A mod that computes without yielding holds one of the two, delaying
  the mods behind it. One that neither yields nor allocates stops the host at its next collection. The daemon pings the
  host every 10 s whether or not a request is out, since the kernel's answer bound counts from a request and events
  alone start none; a host that answers no ping for 30 s is ended and started again. Its answer to each ping names the
  mods in a handler and for how long. A host ended while a mod had been in a handler for longer than that starts its
  next generation without that mod and says so on the mod's health line, so a mod that wedges the host stops only
  itself, a shipped one included; `mods.restart` brings it back.
- A handler that throws is skipped and counted, its last error kept on the mod's health line. A mod's queue is bounded:
  the oldest events give way (requests and the record's lines never do), and the next event the mod receives says how
  many in `dropped`.
  Requests are coalesced: at most one queued `preview` per connection and mod, and one `tree_children` per mod and
  id; a newer request replaces an older one, which is answered `superseded`. A request still unanswered after 10 s is
  answered `mod_busy` by the daemon, and the window asks again at the mod's next `changed`. The host never runs it:
  each request carries its deadline, and a mod's task skips one whose deadline has passed, since a caller's bound
  alone cancels nothing (sidecars guarantee 3's limits).
- `changed` is coalesced in the host to at most once a second per node, the one bound on how often a pinned chart is
  drawn again.
- A restart reloads every mod: the op `mods.restart`, run by `sot-fe mods restart`. The first build uses no Revise.

## Events

| Kind | Source | When | Data owner | First build |
|---|---|---|---|---|
| `:rows` | the daemon's row registry, forwarded to the host | when the host subscribes, and after each `workspace.changed`, coalesced over 200 ms (the registry poll publishes work-state changes there) | rows: `workspace.list`'s rows | built |
| `:agent` | the agent record, read by the host | each line an agent hook appends; never dropped | agents: the record's line format | built |
| `:tick` | the host | once a second, at most one waiting per mod: a mod shows ages to the second | none | built |
| `:repl` | the REPL frame bus, forwarded | a run's start and its end: code, outcome, elapsed time, figure paths | sidecars | later |
| `:files` | the watcher bus, forwarded | `preview.changed` paths | files | later |
| `:monitor` | the monitor tick on the hub, forwarded | each sample | sidecars | later |
| any other symbol | `ShipToolsRepl.emit(kind, data)` in user code, or `sot-fe emit` | when user code or a script calls it; kinds bounded when it is built | the caller | later |

- Subscription is dispatch. A mod hears `K` when `hasmethod(react, Tuple{M, Event{K}})`. The candidate kinds are the
  built ones plus every `Symbol` named in any `react` signature, so a `Union` of kinds is heard kind by kind. A mod
  hears every kind when it has a method for a kind no source names (`Event{:__unnamed__}`), as an untyped
  `react(::M, ::Event)` and a `where K` method do. A `react` method on `Mod` itself would reach every mod of every
  package, so it is named on the health line of the package that defines it. The host computes this after loading and
  again whenever `Base.get_world_counter()` has moved, and sends the daemon `subscribe {kinds}` each time; the daemon
  forwards only those kinds. An ambiguous method is named on the mod's health line, never skipped silently.
- A forwarded kind is live only. A fresh host gets a `:rows` snapshot at once, which replaces what any lost one said.
- The daemon's forward to the host is one bounded channel, lossy like the daemon's buses, its drops counted and shown.
- An event is never mail. Mail stays the one verb that crosses from a session to a session.

## The agent record: Claude Code's hooks as one event source

- The writer is `sotd agent-record`, a subcommand of the daemon's own binary, owned by agents beside `sotd agent-exec`
  (`rust/backend/src/agents/ops.rs`). Like `trust declare`, `comm` and `work-state`, the binary's entry dispatches it
  before anything of the daemon starts, with their private umask (`rust/backend/src/main.rs`). Each of
  `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PermissionDenied`,
  `SubagentStart`, `SubagentStop`, `Stop`, `StopFailure`, `Notification`, `PreCompact` and `SessionEnd` starts it as a
  command hook. The hook has `"async": true`, Claude Code's own fire-and-forget: it runs in
  the background and never blocks the turn. It is in exec form (`args`, no shell), at the path the daemon already
  gives its legs as `SOTD_BIN` (`own_sotd_bin`, `rust/backend/src/agents/env.rs`). When that value is empty (the
  daemon's start path is not a runnable file), the leg names no recorder hook. Rust for plumbing:
  - no bash and no jq on the per-event path;
  - one bounded write per line;
  - the folder rule and the line's byte bound tested in Rust.
- The registration is the agents layer's. A leg of the recipe already carries the layer's work-state hooks in its one
  `--settings`, merged with the auto-memory key when that store is proven (`hooks_settings` and `merged_settings`,
  `rust/backend/src/agents/layer.rs`, called from `claude_recipe` in `argv.rs`). A caller's own `--settings` that is
  one JSON object gains them (`merge_caller_settings`). The recorder's thirteen entries join that table. The builder
  learns the two ways they differ from today's entries, exec form and `"async": true`, and its duplicate check, which
  reads a hook's `command`, reads `args` too.
  - A leg carries the recorder hooks exactly when it carries the layer. A caller's `--settings` that is a file path,
    or one of several, gets none, as it gets no work-state hooks, and the recipe says so.
  - No account's `settings.json` changes, and a plain `claude` (a `claude -p` that a session starts) runs without them.
  - `ccb` builds the same recipe through `sotd agent-exec`, by ADR 0046 decision 4, so its sessions carry the hooks
    too. Outside a row `SOT_AGENT_RECORD` is unset and the writer exits having written nothing. A session that carries
    the hooks and inherits a row's environment (a `ccb` started from the row's shell) records into that row as a
    session of its own.
  - The work-state hooks stay as they are, three in the layer and the Stop hook in the person's own settings:
    work-state is rows', the record is agents'.
- Every start of a row's supervisor reaches one launch, rows' `spawn_detached_supervisor`
  (`rust/backend/src/rows/spawn/detach.rs`): a fresh row, a reauth and a watchdog's replacement alike. It makes the
  row's folder in the record, private (0700), and agents' leg environment (`capsule_supervisor_env`, `env.rs`) names
  it as `SOT_AGENT_RECORD`. The supervisor keeps that environment for every run it starts, so the capsule learns
  nothing of the record. The writer never makes a folder: with the variable unset or the folder gone, it writes
  nothing. It never writes to stdout, since a `SessionStart` or `UserPromptSubmit` hook's stdout becomes the model's
  context. It projects its input to one line and appends it, in one write, to
  `$SOT_AGENT_RECORD/<UTC date>.jsonl` opened for append. The time and the date come from one read of its own clock.
- The record is `<state dir>/agent-record/<workspace id>/`, keyed by the row's canonical id (`SOT_WORKSPACE_ID`), beside
  the rows' own `<state dir>/workspaces/<id>/` (`rust/backend/src/rows/spawn/state_root.rs`). The state dir is one
  computer's, on a local disk: rows refuse a root on a network disk (`preflight_volume`,
  `rust/platform/src/host/volume.rs`, platform guarantee 8) and on volatile storage. So no host name is needed in the
  path, and each file is appended by one computer's processes on a local disk.
- Agents sweeps the record, at start and once a day: it removes day files older than 30 days, and the empty folder
  of an id no registration names, by rows' whole-load rule (`store::named_workspace_ids`; a load that fails skips
  that part). The rows' own start sweep does not touch the record. For that month, the record is an index into the
  transcripts it names, for inspecting the work after the fact (`requirements.md:53`). It runs about a megabyte per
  busy row a day. It holds the first lines of prompts and commands, which is why it is private.
- A line holds:
  - `v`, the format's version;
  - `t`, in milliseconds by the writer's own clock, since separate hooks append in any order;
  - `hook`, `agent` (`claude`), `session_id`, `prompt_id`, `agent_id` (present only inside a subagent) and
    `agent_type`;
  - `tool_name`, `tool_use_id`, and `duration_ms` (a `PostToolUse` or `PostToolUseFailure`);
  - `is_interrupt` (a `PostToolUseFailure`), and a notification's `notification_type` and text;
  - a one-line summary of the tool's input: a Bash command's first line, a file path, an Agent call's `description`
    and `subagent_type`, or a tool's first string field when the projection does not name the tool;
  - `launched_agent_id`, the `agentId` an Agent call returns, renamed so it is never read as the `agent_id` the hook
    fired in;
  - a prompt's first lines;
  - `transcript_path` (a `SessionStart`) and `agent_transcript_path` (a `SubagentStop`);
  - a `StopFailure`'s `error`, and its `last_assistant_message`'s first lines. A `SubagentStop` carries no last
    message (P2): a subagent's last words reach its parent as a prompt, whose first lines the line already holds.

  The whole line is bounded at 4,000 bytes: the writer cuts the longest strings at a character boundary until it
  fits, so that every platform appends each line whole (P4). The format has its own page beside the writer, as
  `comm/PROTOCOL.md` is the inbox's.
- The host reads the record as a queue.
  - For each mod that hears `:agent`, it keeps a cursor, a byte offset, in each row file. It moves the cursor only
    past a newline, so a line caught half-written waits for its end.
  - A mod is handed its next line only when its queue has room, so `:agent` is never dropped: the file holds what a
    queue would.
  - A fresh host starts every cursor at the beginning of the previous UTC day's file. A mod's history and its live
    events are then one stream with no gap and no duplicate, and work opened up to a day before a restart is in it.
  - The host looks for new lines once a second, in the current and the previous day's files.
  - A line that does not parse is skipped and counted on the mod's health line.
  - Each line reaches the mods as an `Event{:agent}` whose `row` is the workspace id. A mod orders by `t`, never by
    file.
- The record lives on this computer only and is never relayed. Nothing a mod does reaches back into the hook.
- Codex appends to the same record from its hooks with `agent: "codex"`, later.
- Rejected:
  - an `agent.event` op per event, sent by the same short process: it adds a connection and a hello to every event,
    and an event is lost while the daemon or the host is down, where a line in the record waits;
  - a bash and jq script per event: the repository diagnosed hook shells piling up on Windows
    (`comm/work_state/hooks/comm-status-heartbeat.sh`), and jq writes a line over 4 KiB in two writes, which
    interleave with another writer's (P4);
  - an HTTP hook to the daemon, or OpenTelemetry export to a collector in it: each needs a receiver and keeps nothing
    while none listens, and OpenTelemetry has no subagent lifecycle;
  - a TypeScript function-hook mod: Claude Code only, on an early-access API;
  - reading transcripts: files with no versioned format.

## Drawing

- The window gains one navigation mode, Mods; the lane chooses its chord. Its root holds one node per mod loaded on any
  connected computer, labeled with the host's health line for it (loaded, errors, drops, slow, a version shadowed).
  Under a mod, its nodes; when more than one computer runs it, one node per computer first. A daemon of the same
  protocol built before mods answers the op as unknown and is shown as running none; a daemon of another protocol is
  refused at hello, as today.
- On the wire, one sidecars op, `mods.request {call, mod, id, params}`, in `kernel.request`'s shape (the Modules mode
  precedent): `call` is `mods` (the loaded mods and their health), `tree_children` or `preview`, whose reply carries
  the image as `preview.get`'s does. One event, `mods.changed {mod, ids}`, goes to the daemon's connections, and one
  op, `mods.restart`. Files' `tree.*` and `preview.get` stay files'. Neither needs a `PROTOCOL_VERSION` raise: the ops
  are new, and a field added to a request is `#[serde(default)]` (`rust/protocol/CLAUDE.md`, Promises).
- Who holds which part, by the server's contract: wire names the ops and their payloads
  (`rust/protocol/src/ops/`); the binary routes them (`rust/backend/src/server/dispatch.rs`) to sidecars' mod
  service, a handler given its context, which waits on the host off the connection's loop; the `:rows` forward
  reads rows' list and its work-state poll; and `mods.changed` reaches the connections through the server's event
  delivery.
- Previews are drawn by MIME with the renderers the window has: `image/png`, `text/markdown` and `text/plain`. A chart
  is a PNG that CairoMakie draws at the pane's `fit_w` and `fit_h`, so its text is laid out for the pane on a laptop
  and on an ultrawide, it is rasterized in the host and not on the window's thread, and the window gains no renderer. A
  mod's markdown cannot show figures: a markdown figure resolves to a `files:` node of the displayed markdown's
  workspace (`rust/frontend/src/ui/preview/image/figures.rs`).
- In the window, the Mods tree is global in scope, as the Sessions and Hosts trees are (`TreeScope::Global`,
  `rust/frontend/src/ui/nav/tree_store.rs`). A mods preview is current by its own key, (host, mod, id, generation),
  since the active host and workspace key that files previews use (`reply_is_current`,
  `rust/frontend/src/ui/preview/fetch.rs`) would drop every other computer's reply. The cursor follows mods nodes,
  and `p` pins them as it pins files, which today is `files:` nodes only (`toggle_pin`, `preview/pane.rs`).
  `mods.changed` is a typed event of fe-net's (`IncomingEvt`) with its own arm in fe-ui: the window fetches again the
  preview it shows, pinned or not, and lists again an expanded node among the ids. A pinned chart is a live panel
  kept up while the person browses. A mod's node names its row by canonical id, which the window resolves through its
  row owner (`RowDirectory`), never through that owner's storage.
- A node's `payload` may hold `color`, one of the window's work-state color names; the window draws the label in it.
- The window learns no mod: it learns a tree served by a host and a payload drawn by MIME. Tree labels reach the screen
  only through `cell_lines` (`rust/frontend/src/ui/CLAUDE.md`, Promises).
- Later surfaces, built when a mod forces them: a drawer that shows several mod panels at once; badges on Sessions
  rows; interactive WGLMakie pages through the pages server.

## Across computers

Each daemon's host sees its own computer, and the window merges the hosts under each mod, as Sessions mode merges rows
by host. A mod that must act on another computer will do it through mail, which already crosses computers. Nothing is
forwarded between daemons, and the hub link carries no events: only requests the hub answers at once ride it
(`rust/backend/src/comm/mail/hub_link.rs`, `SILENT_PINGS`).

## What a mod may do

In the first build a mod computes, draws and calls `changed`. Its code runs as the person and can do what any Julia
code can. The host offers it no verb into Ship of Tools, because the agents view needs none. The first verbs, added
when a mod forces them, are filing mail (`comm.file`) and showing a result (`fe.command.send`), each an existing op
the host would relay. Typing into a row, or running code in a row's REPL, waits for a case. So does a folder of a
mod's own on this computer: no first-build mod needs one, and a name core exports stays until the next interface
break.

## Security

- A mod that arrives with a cloned repository is inert. The host's load path holds its shipped project, the mods
  environment and the standard library, and nothing else, so nothing in a project folder is ever loaded and no project
  file names a mod. A repository that ships a mod runs it only after it is added to the mods environment
  (`Pkg.develop(path=...)` or `Pkg.add`): that act is the consent. `Pkg.develop` consents to a live folder, whose later
  changes run at the next start. An agent acting as the person can take that act too.
- The environment's `[deps]` is the one list the person keeps: it is Pkg's own file, and adding to it is the act of
  consent. Ship of Tools keeps no second list beside it.
- The kernel never loads a mod.
- The host runs as the person and is not sandboxed, as the REPL is not: the requirements rule out sandboxes and gating
  (`requirements.md:62`). A mod is trusted as a `startup.jl` is. The host is given no page secret.
- An event's text (a prompt, a command line) is data, never instructions, and reaches the screen only through the
  window's paths for untrusted text.
- Any process of the person's account can append to the record, as it can to an inbox: the single-user boundary every
  file of the state folder has.

## The first mod: the agents view

The maintainer chose it, 2026-10-18, and what it shows: each agent's state and current tool, its subagents, and a turn
timeline chart.

- It ships in the host's own project (`julia/mods/AgentsView/`) and loads exactly as a person's mod does.
- State comes from `:rows` (each row's name, agent, account and work-state, on this computer) and `:agent`. History
  arrives through the record's cursors, so the view keeps no copy of it, and a host restart loses nothing opened since
  the start of the previous UTC day.
- A row's state is its work-state, which is rows'; its tool, its turns and its subagents are the record's.
- A row whose record holds no line in what the host has read shows `no record` in place of a tool and a turn. That is
  a leg started before mods were built, a leg without the layer, a caller's `--settings` the recipe could not merge
  into, hooks turned off in the person's settings, or an empty `SOTD_BIN`.
- Each session is a lane of its own, keyed by `session_id`; a subagent is told apart by `agent_id` alone, since
  `agent_type` is also present on the main thread of an `--agent` session.
- A turn runs from `UserPromptSubmit` to `Stop` or `StopFailure`. A subagent's hand-back reaches the main session as
  a prompt of its own, which opens `<agent-message from="<agent_id>">` (P2); the chart draws that turn as the agent's,
  not the person's.
- `Stop` does not run after the person interrupts, so an open turn is also closed by:
  - a `PostToolUseFailure` with `is_interrupt`;
  - an `idle_prompt` notification, which Claude Code sends once the prompt has sat idle (60 s by its hooks guide);
  - the session's next prompt;
  - its `SessionEnd`.

  A turn closed by anything but `Stop` or `StopFailure` ends on the chart at its last line. Headless, an interrupt
  during a tool sends neither of the first two (P2). Until the interactive check shows otherwise, such a turn stays
  open until the next prompt, and its open call is drawn with its age, so a stale one reads as stale.
- A tool call is drawn from its `PostToolUse` or `PostToolUseFailure` with `duration_ms`, so it needs only its end.
  - Its `PreToolUse` makes it the current tool.
  - A `PermissionDenied` ends it: rows run `--permission-mode auto`, whose classifier denies calls.
  - A turn's close closes its open calls.
  - A current tool is shown only while its turn is open, since the last `PostToolUse` can land after the row's
    work-state is idle.
  - A `PreToolUse` that arrives after its end opens nothing.
- A subagent runs from `SubagentStart` to `SubagentStop`. A background subagent is named by the Agent call whose result
  carried its `launched_agent_id` at launch. A foreground subagent's result comes only when it ends, so while it runs it
  is named by its type, or by the description of the one open Agent call of that type when exactly one is open. In the
  release checked, every Agent call ran in the background (P2).
- Tree: one node per row, `<row> · <state> · <tool> <age>`, colored by work-state; under it the row's subagents,
  `<name> · <status> · <minutes since it last acted>`, those that ended within the hour dimmed.
- A row's preview is a CairoMakie timeline: the last two hours, a lane per session and per subagent, turn spans, tool
  calls colored by tool, and a title line with the row, its state, its current tool and the first line of its last
  prompt. A subagent's preview is its own lane, its type and description, and the first lines of its hand-back.
- It calls `changed` for a row on each of its events and for the ages on `:tick` once a minute; the host's coalescing
  bounds the redraws. The chart is drawn only when a window asks, so nothing is drawn that nobody watches. CairoMakie
  loads, on the mod's own task, at the first preview. A preview asked for while it loads is answered `mod_busy` by the
  daemon at the request bound, and the view calls `changed` for its rows once CairoMakie has loaded.
- It replaces the planned native Agents mode, never built (`docs/src/guide/modes.md`), and the earlier study's
  cross-row plan for it (a registry field, a `workspace.list` field, child rows in the Sessions tree).
- Limit: it shows the rows of computers whose daemon the window reaches. A session on a computer with no daemon is not
  shown, because nothing there records it.

## What is deleted

- The desktop route: the TypeScript mod, its `.sot/mods/<mod>.svg` file convention and the `--plugin-dir` flag in
  `claude_recipe`. None was built, and none will be. The preview pane's SVG renderer stays: markdown figures and math
  use it.
- `Mode`, `Tool` and `Capture`, on the schedule under "The mod". `Mod` takes `Mode`'s place, with
  `tree_children` and the 3-argument `preview` in place of the unbuilt `tree_root`, `tree_children` and `preview_for`.
  `Tool` went with the orchestrator, since the agents are Claude Code and Codex in rows: a mod that offers agents a tool
  would do it as an MCP server, a decision for when one is wanted. `Capture` is replaced by `:repl` events.
- ADR 0006: the `[sot].extensions` list is never built. It was a way for a project file to load code. What is not
  shipped loads in the mod host from the mods environment; a third-party `FileType` will load there too, the daemon
  asking the host after the kernel declines, as a later step.
- ADR 0007: no orchestrator, no static tool registration.
- The planned Agents and Outputs modes become mods.
- Kept as they are: `FileType` in the kernel; `ConceptEntity` and `AnnotationKind`, which belong to the concept layer's
  own design; the Monitor drawer, which may become a mod later.
- Asked and not added: replay of forwarded kinds, a mod manifest, lists that enable or disable a mod, per-mod
  permissions, a sandbox, and before, block or rewrite hooks.

## Premises and their tests

- P1: an async hook in exec form writes its line on Linux, macOS and Windows, a `SessionEnd`'s included (its hooks
  have 1.5 s by default). Reported, on Windows: the CPU per line with a large `tool_response`, and the number of writer
  processes alive at once in the busiest hour. What stands if it fails:
  - if one hook's line is lost on a platform, the view's closing rules that do without it (the next prompt,
    `idle_prompt`) stand there, and this record is amended to say so;
  - if lines are lost in general, item 2 stops for a new decision.
- P2: on the Claude Code release in use, the types say, and a live check before item 4 starts confirms, that:
  - `SubagentStart` and `SubagentStop` carry `agent_id` and `agent_type`, and a tool call inside a subagent carries
    its `agent_id`;
  - a background Agent call's `PostToolUse` carries the new `agentId`;
  - `StopFailure` fires on an API error;
  - `PermissionDenied` fires when auto mode denies a call, and whether a `PostToolUse` or `PostToolUseFailure` follows
    it is recorded;
  - a `PostToolUseFailure` carries `is_interrupt`, and an `idle_prompt` notification comes after an interrupt.

  That `Stop` does not fire after an interrupt is the hooks guide's word, not the types', and the same live check
  confirms it.
- P3: hooks given by the recipe's `--settings` run alongside the account's own (the work-state hooks still fire). The
  2.1.303 binary lists them as a source of their own, enabled by the same rule as user settings; the live check stays,
  and since the layer's work-state hooks now ride the same `--settings`, a leg's own composition is the build's check.
- P4: eight copies of the writer, each fed the longest line its projection can make, appending a thousand lines each
  to one file leave no line torn or lost, on Linux, macOS and Windows.

### Checked 2026-10-22, Claude Code 2.1.308

Throwaway checks, nothing built. Each run was a headless `claude -p --permission-mode auto` in a scratch folder. It
had a scratch `--settings` file that registered one recorder hook, which saved each hook input whole, for the thirteen
events above. It had `--include-hook-events` and `--debug=hooks`, and the work-state hooks were stood down by
`SOT_COMM_HOOKS=off`.

- P2, mostly holds.
  - `SubagentStart` and `SubagentStop` carry `agent_id` and `agent_type`, and a tool call inside a subagent carries
    both.
  - A background Agent call's `PostToolUse` carries the new `agentId` in `tool_response`, beside `isAsync`,
    `description` and `status`.
  - An unknown model fires `StopFailure` with `error: "model_not_found"` and `last_assistant_message`, and no `Stop`.
  - Three things the design had assumed otherwise:
    - `SubagentStop` carries no `last_assistant_message`; a subagent's hand-back reaches the main session as a
      `UserPromptSubmit` whose prompt opens `<agent-message from="<agent_id>">`, under a new `prompt_id`;
    - both Agent calls ran in the background, the one the prompt asked to run in the foreground included;
    - `UserPromptSubmit` carries no `source`.
  - `Stop` and `SubagentStop` carry `background_tasks`, each running subagent's id, type, status and description.
  - Headless, an interrupt (the stream-json `interrupt` control request, about 6 s into a 30 s Bash call) sent no
    `PostToolUseFailure` and no `Stop`: the call's `PreToolUse` was the last line until the next prompt. No
    `Notification` came in the 75 s idle that followed.
  - Open: `PermissionDenied`, which needs a call the classifier denies (two harmless asks were allowed, and a
    self-permission ask was refused by the checking session's own classifier before it ran); and an interrupt with
    Esc in an interactive session, `is_interrupt` and `idle_prompt` with it. Both need a person-run check.
- P3 holds. In one run's debug log, the scratch hook and the account's hooks ran for the same events: the work-state
  hooks on `UserPromptSubmit`, `PostToolUse` and `Stop`, and the account's `PreToolUse` guard.
- P4 holds on Linux. Eight processes appended 1,000 lines each to one file on a local ext4 disk (kernel 5.15), one
  `write` per line with O_APPEND, the planned writer's shape. Line sizes were 512 B, 3,999 B, 4 KiB, 8 KiB, 64 KiB and
  1 MiB. There were no short writes, and no torn or lost lines, at any size. The torn lines the second review measured
  came from jq writing one line in two writes, not from the file system. macOS and Windows were not checked, and the
  4,000-byte bound stays for them.
- P5: the host's resident memory idle and after CairoMakie loads, the first chart's time on a prepared install, and
  what CairoMakie adds to the prepare and the depot. Reported, not gated.
- P6: the record's lines per minute in the busiest hour of a day with many rows, and the time a fresh host takes to
  hand each mod a day of history; the mods' queue bound is set from it.

## Consequences

- The extension story becomes one sentence: a package that defines a `FileType` or a `Mod` and is loaded where its
  host looks.
- Every later surface (Outputs, a live experiment dashboard fed by `emit`, figure provenance from `:repl` events) is a
  mod against the same declarations, not a native view.
- Each agent action is on disk, per row, for a month, whether or not a mod reads it.
- A computer runs one more Julia process for as long as its daemon runs, and CairoMakie's memory once a chart is drawn.
- Each Claude hook event starts one short background `sotd` process.
- A mod sees only its own computer. A view across computers is a merge in the window, not a correlation in a mod; one
  that must correlate across computers waits for mail as a verb or a later decision.
