The REPL ​

This is the deep dive: the frame schema, dispatch semantics, and figure-rendering mechanics. For the drawer's layout, keys, and how to drive it day-to-day, see REPL Pane.

Ship of Tools keeps a persistent Julia REPL available throughout a session. It is your interactive Julia session — the same bindings, the same loaded packages — but its output is structured, and the figures it produces render inline in the native window rather than as text.

The REPL drawer toggles with Primary+j (Ctrl+J on Windows and Linux, ⌘J on macOS).

The drawer is Ship of Tools' own input line, not Julia's REPL: ] at the start of an empty line enters pkg mode (pkg>, run through Pkg.REPLMode), Backspace on an empty pkg line leaves it, Up/Down recall earlier inputs, and Ctrl+C interrupts a running evaluation. There is no ? help mode, no ; shell mode and no Tab completion; use the Terminal drawer or the agent pane for shell commands.

The REPL and the kernel run the julia that SOT_JULIA_BIN names, else juliaup's default channel, else a julia on PATH. Both start with --startup-file=no. The REPL then loads your depot's config/startup.jl (DEPOT_PATH[1]/config/startup.jl, usually ~/.julia/config/startup.jl) itself, with its standard output pointed at its standard error, so what the file prints shows as error output; a file that throws is reported once, at your first evaluation, and the REPL still starts. The kernel never loads it, because it never runs your code. Julia processes your code starts with Base.julia_cmd() also get --startup-file=no.

A supervised, separate process ​

The REPL is a Julia process supervised by the backend daemon, distinct from the Julia kernel that does project introspection. They are separate on purpose:

  • The kernel owns dispatch tables, mode trees, indexing, and AST hashing.

  • The REPL owns your interactive state — variables you defined, packages you loaded.

Because they are different processes, killing the REPL does not kill the kernel. You can tear down and restart your interactive session — to clear state or recover from a wedged computation — without losing the project view, the mode trees, or the index. (In-memory REPL bindings are not expected to survive a restart, and neither is anything in the REPL's own temporary folder, tempdir(), which goes with its process; other content on disk always does.)

Dispatching code ​

You drive the REPL two ways, without retyping code:

  • Run a whole .jl file from Files mode. Shift+R includes the cursored file into the current persistent session, so its definitions land in your interactive state. r restarts the REPL in the session's project (the session root when it has a Project.toml, else the nearest Project.toml above the file) and runs the file there.

  • Type at the prompt in the REPL drawer. Enter submits the input; Shift+Enter inserts a newline, so you can build a multi-line entry before submitting.

Per-line and per-block dispatch — running just the line at the cursor, or the surrounding top-level form computed by the kernel — are planned, not yet built.

An evaluation runs on its own task, so whenever it yields (sleep, I/O that waits, yield()) the REPL reads the next request, and you can interrupt it mid-eval.

  • An interrupt schedules a real InterruptException onto the running evaluation, the same semantics as Ctrl-C in the stock REPL, which surfaces as an error frame. It reaches only the evaluation's own code and the display of its value (a figure rendering, for example): an interrupt sent before that starts stops it before it runs, and one sent after it has finished does nothing.

  • An evaluation that never yields (a tight numeric loop, a long ccall) holds the REPL's one thread, so the REPL cannot read the interrupt. When an interrupt that names the running evaluation (or names none) has gone a second unanswered, the daemon sends the REPL one interrupt signal, as Ctrl-C does to the stock REPL. Julia raises it at the code's next safepoint, which stops an allocating or calling loop, and holds it through C code (BLAS), compiling and garbage collection until they return. The REPL keeps everything it defined. Code with no safepoint at all (while true end) ignores that one signal, and the interrupt is answered with an error that says so.

  • A second Ctrl+C in the drawer while the same evaluations run, or sot-fe repl interrupt <ws> --force, forces it: a burst of signals, which Julia forces into code with none (it prints WARNING: Force throwing a SIGINT in the evaluation's output). Under heavy CPU load forcing may not stop it (sot-fe repl interrupt --force then answers with an error that says so). Forcing can crash or hang the REPL when the thread is inside C code (a BLAS call is a measured crash), compiling or collecting garbage, and the REPL's state is then lost; --fresh restarts it.

  • The daemon sends a signal only for an evaluation it has seen start and not finish, never to an idle REPL, though it cannot see an evaluation that has just finished and whose done it has not yet read. On Windows the signal is a Ctrl+Break to the REPL's console process group, which reaches every process in it, a server an earlier evaluation left running with run(cmd; wait = false) included, and a console program's default Ctrl+Break handler ends it.

  • Code that catches the InterruptException and goes on still holds the REPL (sot-fe repl interrupt says so after 10 s). A restart ends it at once: r on a .jl file in Files mode, or sot-fe repl run <ws> <path> --fresh, whose run every window's drawer shows.

  • On Julia 1.12, 1 of 20 interrupts of a loop that ends on its own at that very moment was answered with an error (InterruptException, code repl_exception) while the REPL kept running and kept its state; a signal that arrives as the REPL idles between evaluations can end it on 1.12, which only a synthetic signal has produced.

  • Ctrl+C in the drawer names, by number, the evaluations the drawer shows as running, and stops the running evaluation only if its number is one of them (an interrupt that names other evaluations sends no signal). Every drawer on a row shows every run on it: its own, another window's (labeled ⟨window ▸ …⟩) and a session's (labeled ⟨session ▸ …⟩).

  • If the link to a computer drops while an evaluation runs, its entry says so and keeps what it had printed; when the window reconnects and the evaluation is still running, the entry says the connection is back and shows the rest, and Ctrl+C stops it.

How agents use the REPL ​

Claude Code sessions run code in the same REPL you use, the session's own, through the sot-fe repl command that the julia-repl skill teaches them. That REPL starts with --project set to the session root's directory, whether or not it has a Project.toml. The skill is installed for Claude Code only (see What the installer changes); Codex sessions have no REPL skill yet. The REPL runs one evaluation at a time; a request that arrives while another runs comes back busy (see Hosts, sessions, REPLs).

CommandWhat it does
sot-fe repl run <ws> <path>run a .jl file and return its output
sot-fe repl eval <ws> --code '<julia>'run a chunk of code and return its output
sot-fe repl status [<ws>]report whether the workspace has a live REPL
sot-fe repl interrupt <ws>stop a running evaluation, keeping loaded packages
sot-fe repl run <ws> <path> --freshrestart the REPL in the session's project, then run the file; the run's output goes to every window's drawer, not to the caller

<ws> is the workspace id, label or slug; a session finds its own id in $SOT_WORKSPACE_ID. The call returns the collected stdout, stderr, value and errors to the agent. Figures are written to files under <workspace>/.sot/runs/<run_id>/ and the agent gets their paths; it can then put one in your preview pane with show-result <path>. Nothing adds .sot/ to your project's .gitignore — add it yourself.

run and eval print outcome: <outcome> on their first line and exit 0 only for ok, else 2, so read the outcome (run --fresh prints fresh-run accepted: REPL restarted into <dir> (<source>) instead; interrupt exits 3 when there is nothing to interrupt):

  • ok: the run finished. error: it threw (the error follows). interrupted: an interrupt (sot-fe repl interrupt, or Ctrl+C in a drawer) stopped it.

  • busy: another run was going, and nothing ran.

  • timeout: --timeout (default 120 s) passed first. The run is not canceled and keeps going; do not re-run it.

  • restarted: a restart (--fresh, or r in a window) retired the run before it ended.

  • repl_died: the REPL ended first any other way (it died, or its display ended); the next run starts a new REPL.

What this means for you:

  • Every agent run appears in your REPL drawer, labeled with whatever label the caller passed with --origin, or "session" when none is passed. There is no quiet mode.

  • The REPL is shared. Your drawer, the session's agent and its subagents evaluate into the same Main. Definitions an agent makes are there when you type next.

  • One evaluation at a time. A run that arrives while another is going is refused as busy, not queued.

  • A display of its own (Linux). Each REPL gets a private display (an Xvfb), so GLMakie works and its figures come back as files, as CairoMakie's do; interactive figures use WGLMakie with wglshow. A host without Xvfb says so at the REPL's first run (sot: this REPL has no display of its own (...)), and GLMakie does not work there. If the display ends, the REPL ends with it, and your next run starts a new REPL that says why first. A process your code starts, detached or not, ends with that display: at a restart, a --fresh and the REPL's end. On a shared computer the display is the one listener another account can connect to; a 128-bit cookie, which only the REPL holds, is its lock (ADR 0049, "User isolation"). macOS and Windows start no display, since GLMakie draws through the system there.

  • display(x). Inside an evaluation, display(x) reaches the drawer as output of that evaluation.

  • Revise. Ship of Tools does not load Revise; a using Revise in your startup.jl (or in an evaluation) loads it, and the REPL then calls Revise.revise() before each later evaluation, so an edit to a tracked package's src/ or an includet file takes effect on the next one. A revision that fails (a syntax error in the edit) shows as error output of that evaluation, which then runs the old code. Without Revise, re-running a script picks up edits to that script, but an edit to a package's src/ takes effect only after it is included again.

Structured output frames ​

The REPL's display shim emits structured, typed frames instead of a single undifferentiated text stream, so the frontend can render each kind of output correctly. Frames are newline-delimited JSON; the shape borrows IJulia's display_data, flattened so every field sits at the top level of the frame. The backend wraps each frame as a repl.frame event on the main protocol stream.

Frame kindCarries
stdout{text} — streamed incrementally as the evaluation prints
stderr{text} — streamed incrementally
value{mime, text} — the last expression's value rendered as text
image{mime, data_base64, bytes} — e.g. image/png
browser{url, open, fe} — a loopback URL for a live browser-served artifact (wglshow(fig), a BrowserView); open says whether a frontend opens a tab (the window in use; see A second frontend); fe, when present, names the one frontend that opens it
error{message, stacktrace: [{file, line, fn}, …]}
done{eval_id, elapsed_ms} — always the last frame for an evaluation

stdout and stderr stream as the bytes arrive, so you see output as it is produced rather than only at the end. The done frame is the completion signal, correlated by eval_id so the backend can clear the UI spinner for that evaluation. Errors are structured rather than raw stderr text, which lets the frontend render stacktraces with file:line links. Adding a new MIME (HTML, LaTeX, custom) is a frontend-side render change — the frame schema is open via the mime field.

Figures ​

An image value becomes an image frame that the frontend draws inline through the preview layer, never through a terminal graphics protocol (see Frontend Rendering). The walkthrough, with GLMakie and the interactive wglshow, is Figures.

wglshow serves the figure over Bonito on a loopback port the OS assigns, at an address with a secret in it (another account on the box that finds the port gets nothing), and returns a BrowserView, which makes the frontend open the figure in your OS browser with no URL to copy. The frontend hands the browser a one-use local address that redirects to the figure, so the secret is never on a command line. On a remote backend the window relays the page and its WebSocket to the daemon's proxy (ADR 0035), with no setup (see Transport). One server per REPL lives as long as the REPL; calling wglshow again shows the new figure at the same address. With several frontends attached the figure opens in the window in use (A second frontend); wglshow(fig; open = "<fe>") opens it only on the frontend sot-fe --fe <fe> names, and open = false opens it nowhere. A figure has one live viewer: a new tab of a figure stops the earlier tab of the same figure.
